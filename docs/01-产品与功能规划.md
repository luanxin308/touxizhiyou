# 透析之友（touxizhiyou）· 产品与功能规划 v0.1

> 离线安卓 App：拍一下仪器上的数字，把体重、血压、心率记下来，自动算每次透析的排水量，并记住每个月开的药和花了多少钱。
> 目标用户：60–80 岁透析病人本人；家属协助设置与备份。

---

## 一、产品定位

| 项目 | 定义 |
|---|---|
| 一句话 | 透析病人的"体重·血压·开药"口袋本，拍照记录，不联网，字大好看 |
| 使用人 | 血液透析患者（每周 2–3 次），老年为主；家属为次要用户 |
| 使用场景 | ①医院透析室：上机称重、上机量血压 → 下机称重、下机量血压 ②家中：日常称重/量血压 ③每月：开药、算钱 |
| 硬约束 | 全程离线、无需注册、无需联网、数据只存本机、安装包小、低端安卓机可用 |
| 非目标 | 不做诊断建议、不做云端同步、不做医生端、不替代病历 |

### 核心痛点（按优先级）
1. **纸笔记不住**：本子丢、字迹乱，医生查房问"这次涨了多少水"，翻半天翻不到。
2. **数字抄错**：体重秤数码管小、血压计 LCD 反光，老人抄错一位就是几公斤的误差。
3. **药费糊涂账**：一年下来不知道一共花了多少、透析占多少，下个月该怎么调。
4. **现有 App 不友好**：字小、按钮小、层级深、要联网注册。

## 三、核心业务逻辑（务必按此实现）

### 3.1 透析场次模型（数据骨架）

App 的核心实体不是零散的"体重记录"，而是**一次透析（Session）**：

```
Session {
  日期, 班次(上午/下午),
  上机: { 时间, 体重, 收缩压, 舒张压, 心率 },
  下机: { 时间, 体重, 收缩压, 舒张压, 心率 },
  备注
}
```

- 上机、下机各自可以只填一部分（老人可能只测了体重没量血压），任何字段都允许留空。
- 也允许"散记"：不在透析场的单独体重/血压（家中自测），用 `场景=家中` 标记，不进透析量计算，但进趋势图。

### 3.2 透析量（间期增重）公式

| 符号 | 含义 | 举例 |
|---|---|---|
| W_up | 本次**上机前**体重（涨水后） | 10/3 上机 100.0 kg |
| W_down | **上次下机后**体重（干体重附近） | 10/1 下机 98.0 kg |
| ΔW | 本次间期增重 = 本次预计脱水量 | **100.0 − 98.0 = 2.0 kg** |

> 说明：需求原文写作"体重A − 体重B"，但其算式 100 − 98 对应的是 **上机体重 − 上次下机体重**，本方案按语义实现为 `ΔW = W_up − W_down`，界面上标注为"本次排水（间期增重）"，并注明"实际脱水量以医生处方为准"。
> 边界处理：`ΔW < 0`（体重比上次下机还轻）→ 显示但标黄"可能脱水过多/称重有误"；`ΔW > 5 kg` → 标橙提示确认；超过 7 天才配对 → 提示"间隔太久，请核对日期"。

### 3.3 血压提示规则（仅做提示，不做诊断）

| 状态 | 收缩压 | 舒张压 | 展示 |
|---|---|---|---|
| 偏低 | < 90 | < 60 | 蓝色 + "偏低，注意头晕" |
| 正常 | 90–139 | 60–89 | 绿色 + "正常" |
| 偏高 | 140–179 | 90–109 | 橙色 + "偏高" |
| 很高 | ≥ 180 | ≥ 110 | 红色 + "很高，如不适请告知护士" |

心率：< 50 或 > 100 标黄提示。所有提示固定带一行小字："仅供参考，不替代医生判断"。

## 四、拍照识别方案（本项目的技术核心）

### 4.1 调研结论（诚实版）

在 GitHub 上检索"七段数码管识别"，实际可用的开源实现全部是**桌面端 Python/OpenCV 的示例项目**，没有任何一个能直接嵌进安卓 App：

| 项目 | 星数 | 语言 | 能否直接用 |
|---|---|---|---|
| NickTrossa/OCR7SD | 14 | Python | 否，Python + 需 OpenCV 环境 |
| lcferrum/segment-display-ocr | 11 | C++ | 否，AviSynth 滤镜 |
| kool7/Digit_Recognition_Using_OpenCV | 3 | Python | 否 |
| zhuzhenLi/ocr-digital-display | 2 | Python | 否 |
| kylekanderson/Seven-Segment-OCR | 1 | Python | 否 |

通用 OCR（Google ML Kit / Tesseract）对**七段数码管识别率很低**，这是业内公认问题：七段数字的笔画断口、细长段、反光，与 OCR 训练用的印刷字体分布不同。

### 4.2 选定方案：双引擎自研 + 人工确认兜底

```
拍照 → 缩放到 ≤1280px → 灰度 → 自适应二值化(正片/负片各一张) → 形态学闭运算
     → 连通域标记 → 字符候选筛选(高宽比/等高性) → 行聚类 → 从左到右排序
     → 引擎A：七段判段（7 段区域亮灭 → 查 0-9 表）
     → 引擎B：数字模板匹配（多字体归一化模板相关性）
     → 加权融合 + 场景约束（体重/血压合理区间）
     → 大字确认页（每一位可改）→ 入账
```

选它的理由：
- **零依赖、可离线、体积小**（APK 可控制在 3 MB 内），本机无需下载任何 maven 依赖。
- 七段判段对"体重秤、多数血压计"这类真正的七段显示，准确率天然高于通用 OCR（它判断的是"哪几段亮"，而不是"像哪个字"）。
- 引擎 B 覆盖液晶矩阵字体、电视屏等非七段数字。
- 识别结果**永远要人确认**，老人看得清、改得动，识别率不完美也不耽误用。

预期指标（首版）：光照正常、距离 20–40 cm、数字占画面 1/4 以上时，七段显示体≥95%，液晶反光场景≥85%，并对失败情况给明确提示（"没看清，请靠近一点/换个角度/关闪光灯"）。

### 4.3 用户侧容错设计

- 取景框半透明遮罩 + "把数字放进框里"大字提示
- 拍照后可拖一个矩形框选识别区域（家属一次设置，之后自动）
- 识别失败 3 次 → 自动切到大数字键盘手动输入（不卡死流程）
- 每位数字单独可点改，避免"差一位重拍"

## 五、技术架构

### 5.1 为什么是"原生壳 + WebView 前端"

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 纯原生 Java + XML | 性能最好、体积最小 | 大字/圆角/图表全靠手写，开发慢，本机无 AndroidX 依赖（网络受限） | 备选 |
| Flutter | 跨端、UI 快 | 本机无 Flutter SDK，且需下载大量依赖 | 不可行 |
| **原生壳 + WebView** | **零第三方依赖、UI 用 CSS 可控（大字/高对比/圆角）、图表 Canvas 自绘、迭代快、效果图即开发基准** | 旧版 WebView 语法受限（规避方案见下） | **选定** |

- 壳层：Java，仅用 Android framework API（不用 AndroidX，避开依赖下载）。
- 前端：HTML + CSS + ES5 兼容 JS（不用 `?.`、`??`、可选链、top-level await），兼容 Android 7 起各版本 WebView。
- 存储：`localStorage` + JSON 分表（体重/血压/药品/处方/设置），总量 < 1 MB，上限 5 MB 足够。
- 相机：**系统相机 Intent**（成功率最高、老人熟悉、可闪光灯），拍完转 base64 回传页面；另提供相册选择。
- 图表：Canvas 2D 自绘折线/柱状图（不引第三方图表库）。
- 构建：`aapt2 → javac → d8 → zipalign → apksigner`，一个 PowerShell 脚本出 APK，本机已验证工具链齐全。

### 5.2 目录结构

```
touxizhiyou/
├─ android/                 安卓壳工程（Java）
│  ├─ AndroidManifest.xml
│  ├─ src/com/touxizhiyou/app/{MainActivity,NativeBridge}.java
│  └─ res/                  图标、主题、字符串
├─ app/assets/              前端（打包进 APK 的 assets）
│  ├─ index.html
│  ├─ css/app.css
│  └─ js/{store,ocr,chart,ui,seed,util}.js
├─ tools/build.ps1          一键构建脚本
├─ proto/                   可交互效果图原型（HTML，浏览器可点）
├─ docs/                    需求、方案、识别设计、适老化规范
└─ dist/                    输出 APK
```

### 5.3 兼容与性能

- 最低支持 Android 7.0（API 24），targetSdk 34。
- 识别在 JS 主线程做，大图先缩到 1280 宽；单张识别目标 < 600 ms（低端机），期间显示"正在识别…"。
- 列表分页渲染（每次 30 条），避免几百条数据卡顿。

## 七、界面与适老化规范

### 7.1 数值规范

| 项目 | 值 |
|---|---|
| 正文 | 20px（可在设置放大到 24/28px） |
| 页面标题 | 30px 加粗 |
| 关键数字（体重/血压） | 56–76px 加粗 |
| 按钮高度 | ≥ 64px，主按钮 80px |
| 圆角 | 16px；卡片 20px |
| 卡片间距 | 16px；页面左右边距 20px |
| 最小可点区域 | 56×56px |
| 对比度 | 正文文字 ≥ 7:1，不使用浅灰小字 |

### 7.2 配色

- 背景 `#FBF4E9`（暖米黄），卡片 `#FFFFFF`，主色 `#E8710A`（橙），深橙 `#B85500`、浅橙底 `#FFF1DE`、卡片描边 `#EDE0C8`
- 文字 `#2E2418`（近黑），次要 `#6E5B44`（仍高对比），辅助 `#A08B70`（只用于时间戳等非关键信息）
- 语义：正常绿 `#3B7A2F`/底 `#ECF5E6`、偏高橙 `#B85500`/底 `#FFF1DE`、很高红 `#C0392B`/底 `#FBEAE7`、需注意黄 `#9C6B00`/底 `#FCF1D5`——均同时给**文字标签**，不单靠颜色
- 按钮一律大色块 + 白字（主按钮橙色渐变 + 底部 5px 深橙硬阴影，制造"按得下去"的立体感），不用纯图标按钮

### 7.3 导航（底部 5 项，图标 + 文字）

`首页` · `体重` · `拍照`（中间放大圆形主按钮）· `血压` · `开药`

### 7.4 页面清单（12 屏）

1. 首页（今日概览 + 三大入口）
2. 体重 · 录入（上机/下机切换，大数字键盘）
3. 拍照取景（相机/相册 + 遮罩提示）
4. 识别确认（大数字、逐位修改、重拍）
5. 体重 · 历史（按场次卡片列表）
6. 体重 · 趋势（双折线 + 区间切换）
7. 血压 · 记录（上机/下机 + 三输入）
8. 血压 · 历史与趋势

### 7.5 交互禁忌

- ❌ 滑动删除（误触风险）→ 改为条目内"编辑/删除"按钮 + 二次确认
- ❌ 只靠颜色区分状态 → 颜色 + 文字 + 图标三重
- ❌ 三级以上页面跳转 → 最多两级
- ❌ 自动弹窗、倒计时、隐藏手势
- ✅ 每个输入框都有超大标签与示例占位；错误提示写"该怎么办"而不是"错误码"

## 九、风险与对策

| # | 风险 | 影响 | 对策 |
|---|---|---|---|
